# 16 Agent 团队：当前实现与真正协作的区别

## 直接结论

当前没有真正的多 Agent 协同执行。界面中的 19 个 Agent 是职责目录与模型配置，不是 19 个正在运行的智能体。六个工作单元也是展示分组，不是六个进程。没有给这些角色发送模型请求，没有它们之间的对话，也没有生成或审稿结果。

这个版本已实现的是流程管理、依赖校验、模型选择、人工产物、版本追踪与拍板。角色名称用于说明“该步骤由谁负责”；不能把这一层配置当作自动化已经完成。页面现在直接展示这一状态。

## 1. 点击“自动推进”究竟发生什么

1. 浏览器提交 `POST /api/v1/commands`，命令为 `PLAN_PROJECT`，参数包含作品 ID、`execute: true` 和当前 `expectedVersion`。
2. `WorkspaceService.execute` 在事务中检查工作区版本；版本冲突返回 409。
3. `plan` 按目录顺序找出未完成、且依赖和阶段拍板满足的节点。若存在待确认阶段，优先说明待人工拍板。
4. 新增一条任务记录，状态为 `BLOCKED`，说明“尚未接入自动执行器”。节点产物和完成状态不会因此改变。
5. 保存到数据库，返回新工作区。未启动后端时，前端领域层执行同样的确定性规则，并保存在浏览器。

这里没有调用 LLM。`plan` 不是让统筹 Agent 推理出来的计划，它是 Java/TypeScript 规则代码。按钮现在代表自动执行前提检查，真正生产仍未接入。

## 2. 角色目录如何参与流程

`specs/agents.json` 定义 19 个角色的职责与工作单元，`specs/nodes.json` 的 `agentRole` 指定节点所属角色。构建脚本把目录同步到前后端。

例如脚本节点归属脚本职责，事实检查节点归属核验职责。界面依据这些字段展示负责者、推荐能力和默认模型。当前没有可执行的角色系统提示词装配、独立记忆、工具调用循环或委派协议；设计文档中的提示词策略仍属于待实现规格。

## 3. 模型如何选择

界面顶部可选全局默认模型，每个角色、作品、节点都可以另设默认模型，也可按能力单独覆盖。全部不覆盖时继承全局。

实际解析顺序：

1. 节点的该能力覆盖 → 节点默认模型。
2. 作品的该能力覆盖 → 作品默认模型。
3. 角色的该能力覆盖 → 角色默认模型。
4. 全局的该能力默认 → 全局默认模型。

每一候选都必须声明支持所需能力，否则继续寻找兼容候选。例如默认语言模型没有 TTS 能力，配音不会错误使用它；需要为 TTS 单独配置模型。能力声明尚未经过真实服务测试，模型档案仍标记待验证。

这些选择已经持久化，但还没有传给执行器。保存配置不产生模型调用，不读取真实密钥。

## 4. 真正多 Agent 协作应该如何实施（尚未实现）

建议使用一个持久调度器，加多个有独立职责和上下文的逻辑 Agent。Agent 不必对应独立机器或进程，也不必使用不同模型。决定是否真协作的是独立任务执行、明确交接和可核验日志。

| 组件 | 工作 | 当前状态 |
| --- | --- | --- |
| 编排器 | 将目标拆为有依赖的任务；并行无依赖分支；等待人工确认 | 有确定性前提检查，未实现智能规划与调度 |
| 角色执行器 | 装配职责提示词、节点输入、允许工具和输出约束，实际调用模型 | 未实现 |
| 模型适配器 | 把统一请求转为各供应商协议，解析响应、用量和错误 | 未实现 |
| 上下文装配 | 只提供已采用且版本确定的上游产物，控制长度并保留来源 | 有人工产物版本，未实现模型上下文装配 |
| 交接合同 | 任务 ID、角色、输入版本、模型快照、输出引用、证据与缺项 | 设计规格存在，未实现执行交接 |
| 质检与返工 | 核验角色审查脚本、证据、时长与格式，反馈给创作角色 | 有人工标准与失效规则，未实现模型审查循环 |
| 持久任务队列 | 排队、并发限制、重试、取消、幂等、崩溃恢复 | 未实现；当前任务是检查记录 |
| 预算与工具权限 | 真实调用前预算预占，限制工具和执行范围，记账真实用量 | 有项目预算字段，未实现执行限额 |
| 人工拍板 | 针对明确产物版本批准关键阶段 | 已实现六阶段人工拍板 |
| 可观测性 | 查看真实请求、响应、交接、工具结果、失败和用量 | 未实现模型调用日志 |

一次目标流程示例：统筹读取选题 → 研究角色检索与交付来源 → 核验角色检查证据 → 编剧生成脚本 → 审稿角色指出具体问题 → 编剧修订 → 人确认 G03 → 制作角色安排素材。研究与风格参考可在独立输入下并行；编剧必须等待采用的证据。审稿有重试上限，失败应交还人工，不允许无限互相聊天。

ComfyUI 等外部生成工具属于制作角色的工具适配器；按用户要求继续只保留异机接入流程。

## 5. 怎样验收它不是“假装多 Agent”

- 能打开每个角色真实运行记录：明确的任务、输入版本、使用模型、执行开始/结束、响应和输出。
- 能看到至少一次跨角色交接，以及审稿发现问题后产生有引用关系的修订。
- 模型不可达时显示失败或等待；不能用示例文本伪造成功。
- 人工拒绝 G03 后，制作角色不能越过它开始付费生成。
- 重启服务后任务可恢复，重复提交不会产生重复费用；取消和预算限制实际有效。

只有完成上述执行链，才可以把产品称为真正的多 Agent 自动化工作台。使用同一个模型扮演多个职责并不天然是假协作，但仅展示多个角色名称和下拉框确实不等于协作。

## 6. 对照当前代码

| 文件 | 实际职责 |
| --- | --- |
| `specs/agents.json`、`specs/nodes.json` | 角色与节点目录 |
| `frontend/src/pages/Hub.vue` | 角色配置、流程上下文、任务记录 |
| `frontend/src/lib/domain.ts` 的 `resolveModel` | 按能力解析继承模型 |
| 同文件 `applyCommand` 的 `PLAN_PROJECT` | 浏览器模式规则检查 |
| `backend/src/main/java/cn/creator/workbench/service/WorkspaceService.java` 的 `plan` | 服务端规则检查与任务保存 |
| `frontend/src/components/ModelDefaultSelect.vue` | 各范围默认模型选择 |

以上代码不存在模型 SDK 调用、Agent 会话或并行执行。后续推荐先打通“研究 → 脚本 → 审稿 → 人工确认”的最小真实链路，取得可观测执行记录，再扩展其他角色。
